# 🤖 日常更新指南（给日常维护 AI 和人类新手）

> 本文档教两件事：**这个仓库每天是怎么自动更新的**，以及**一个 AI（或人）接手日常维护后
> 该按什么步骤干活**。全程简体中文，每一步都给出具体命令，照着做就行。
>
> 规则类细节（分类规则、数据格式、禁止事项）在 [AGENT.md](../AGENT.md)，
> 架构与历史在 [DEV_GUIDE.md](../DEV_GUIDE.md)。**本文档 + AGENT.md 是日常维护的全部必读。**

## 一、先分清：这个仓库有两个 AI 角色

| | 🛠 开发 AI（能力强） | 🔄 日常更新 AI（能力弱一点） |
|---|---|---|
| **是谁** | 被用户请来开发功能、修 bug、改架构的 AI（如 Claude/GPT/GLM 旗舰模型会话） | 负责按文档例行维护仓库的 AI，或在 Actions 里内置调用的 AI API |
| **什么时候出场** | 用户主动要求改东西时 | 每天/每次例行维护时 |
| **能做什么** | 改 `scripts/` 代码、改 workflow、改文档、加解析器、跑全量测试 | 只按本文档的 SOP 跑流程、看日志、处理 PENDING_URLS、报告异常；**不改代码** |
| **遵循什么** | AGENT.md（操作规范）+ DEV_GUIDE.md（架构） | **本文档就够了** |
| **改坏了怎么办** | 自己负责修 | 回滚到上一个正常 commit（见第五节），并报告用户 |

**一句话**：日常更新 AI 的原则是"**照章办事，不动代码**"。需要改代码的活，转告用户找开发 AI。

> 补充说明：Actions 里面**还内置了一个 AI API 调用**（`ai_client.py`，主力 ChatAnywhere
> `gpt-6.1-sol`），它只干一件小事——理解 `PENDING_URLS.md` 里用户写的自然语言条目。
> 它不是"维护 AI"，只是流水线上的一个解析器，抓数据完全用不到它。

## 二、仓库每天是怎么自动更新的（不需要任何人干预）

GitHub Actions 每天按 6 个时段自动运行（cron 都避开整点，减轻源网站压力）：

| 北京时间 | cron (UTC) | 模式 | 干什么 |
|---------|-----------|------|-------|
| 05:17 | `17 21 * * *` | `ai-cloud` | 抓云厂商活动页（华为云/阿里云/腾讯云/腾讯 WorkBuddy） |
| 08:23 | `23 0 * * *` | `ai-blog` | 抓博客聚合（异次元/小众软件等，自动分流开源工具） |
| 11:41 | `41 2 * * *` | `drive` | 抓 V2EX 开车线报 |
| 13:37 | `37 5 * * *` | `games-direct` | Epic/Steam/GOG 官方 API |
| 15:53 | `53 7 * * *` | `games-blog,game-discount` | ITAD/itch.io/Reddit + 小黑盒（Playwright 渲染） |
| 18:47 | `47 10 * * *` | `finalize` | 整理阶段（见下） |

**finalize 阶段**（每天最重要的一次）依次做：

1. **处理 `PENDING_URLS.md`**：把用户提交的 URL 登记并当场抓取入库；
   自然语言条目交给 AI 解析；处理完自动移到「已处理」区并附结果
2. **归档过期活动**：把已结束/过了截止日的活动按月写入 `docs/archive/YYYY-MM.md`，
   并从主数据移除——所以 README 里永远不会出现过期活动
3. **重新生成产物**：`docs/data/*.json`（前端数据）→ `docs/calendar.svg`（甘特图）→
   `README.md`（含统计与分类表格）
4. **自动提交**：用 bot 身份 commit（`chore(data): {mode} update {日期}`）并推送

每个时段跑完都会自动提交一次。**你什么都不做，仓库也能正常运转。**

## 三、Actions 里的 AI 怎么配置（要改就改这一处）

AI 配置在 `.github/workflows/daily-collect.yml` 的「运行收集脚本」步骤的 env 里：

```yaml
AI_BASE_URL: https://api.chatanywhere.tech/v1     # 主力中转站
AI_API_KEY: ${{ secrets.AI_API_KEY }}             # key 存在 GitHub Secret，不在代码里
AI_MODEL: gpt-6.1-sol                             # 主力模型
AI_FALLBACK_BASE_URL: https://api.siliconflow.cn/v1  # 备用中转站
AI_FALLBACK_API_KEY: ${{ secrets.AI_FALLBACK_API_KEY }}
AI_FALLBACK_MODEL: deepseek-ai/DeepSeek-V3.2
```

**换模型/换中转站的步骤**（日常 AI 也能做，就是改 3 行）：

1. 编辑 `.github/workflows/daily-collect.yml`，改上面的 `AI_BASE_URL` / `AI_MODEL`
2. 确保对应的 Secret（`AI_API_KEY` 或 `AI_FALLBACK_API_KEY`）里存的是新服务的 key：
   仓库 **Settings → Secrets and variables → Actions** 里更新（人类在网页点几下；
   AI 可用 GitHub API 的 `PUT /repos/{owner}/{repo}/actions/secrets/{name}`，值要用
   libsodium sealed box 加密，参考 DEV_GUIDE.md 第 7 节的代码）
3. 提交推送后，在 Actions 页手动 Run workflow 验证一次（模式选 `finalize` 最快）

**当前 key 实测可用的 19 个模型清单**：见 [AGENT.md 13.1.1](../AGENT.md)。
选型参考：`gpt-6.1-sol`（最强最稳，默认）> `deepseek-v4.1-flash`（便宜）> `gpt-5-mini`（轻量）。

**额度**：AI 只在 PENDING_URLS 有自然语言条目时才调用（日常 0 次），
ChatAnywhere 免费版（每周 50000 点 + 每天 100 请求）绰绰有余。
主力连续 3 次失败（401/欠费/超时）会自动切备用，不用人管。

## 四、日常更新 AI 的标准作业程序（SOP）

当你（维护 AI）被叫来"更新一下仓库 / 跑一次 / 检查一下"时，**严格按以下顺序做**：

### 第 1 步：同步远程（防止别人/Actions 刚推过）

```bash
git fetch origin
git rebase origin/main     # 有冲突先解决，原则：以远程为准
```

### 第 2 步：跑一次 finalize（最安全、最常用）

```bash
pip install -r scripts/requirements.txt        # 首次才需要
export GITHUB_REPOSITORY="<owner>/wool-gathering"   # Windows PowerShell: $env:GITHUB_REPOSITORY="..."
python scripts/collect.py finalize
```

它会：处理 PENDING_URLS → 归档过期活动 → 重新生成 SVG/README/前端数据。
**这一步不抓网络、不需要 AI Key、不会抓坏数据**，日常 90% 的请求用它就能满足。

### 第 3 步：验证结果（必做，别跳过）

```bash
# ① 看 README 统计区：归档数应单调不减，进行中数量合理
grep "进行中" README.md

# ② 确认没有已结束标记残留（应为 0）
grep -c "⚫" README.md docs/分类活动.md

# ③ 确认归档索引存在且条目数 = README 里的"已归档"数
python -c "import json; print(len(json.load(open('docs/archive/index.json'))))"

# ④ 看本次运行日志有没有 ERROR
```

### 第 4 步：按需执行其他模式（用户明确要求时才做）

```bash
python scripts/collect.py ai-cloud        # 仅云厂商
python scripts/collect.py ai-blog         # 仅博客聚合
python scripts/collect.py drive           # 仅 V2EX
python scripts/collect.py games-direct    # 仅 Epic/Steam/GOG API
python scripts/collect.py games-blog,game-discount   # 博客聚合 + 小黑盒（需 Playwright）
python scripts/collect.py all             # 全量 + finalize（约 5-20 分钟）
```

### 第 5 步：提交推送（只有真有变更才提交）

```bash
git add -A
git status --short                        # 确认没有不该提交的东西
git commit -m "chore(data): finalize update $(date +%Y-%m-%d)"
git push origin main                      # 网络失败就重试 2-4 次
```

### 第 6 步：报告

用中文向用户汇报：本次跑了什么、新增/归档多少条、有没有异常。
**失败了就说失败**，附上关键日志行，不要掩饰。

### 例行检查（被要求"检查一下仓库"时额外做）

1. GitHub Actions 页看最近 6 次运行是否全绿（有红叉点进去看日志哪一步挂了）
2. `README.md` 统计区数字是否正常（进行中数量不至于 0 或暴涨）
3. `docs/archive/index.json` 的条目数和 README"已归档"一致
4. `PENDING_URLS.md` 的「待处理」区是否为空（不空说明上次没跑或失败了）

## 五、出问题时怎么办（故障排查表）

| 症状 | 原因 | 处理 |
|------|------|------|
| Actions 运行红叉 | 看日志定位步骤 | git 冲突→rebase；依赖失败→重跑一次；脚本报错→把日志给用户转开发 AI |
| AI 相关日志 401/欠费 | key 失效或额度尽 | 会自动切备用（看"已切换到备用中转站"日志）；持续失败→换 key（第三节） |
| README 数字没变 | 当天确实没新数据 | 正常，不是 bug |
| SVG 不更新 | Actions 没跑成功或缓存 | 手动触发 `finalize`；浏览器强刷 |
| 某分类长期 0 新增 | 源页面结构变了 | 抓 WARNING 日志给用户，转开发 AI 修解析器 |
| 过期活动又出现在 README | 不应该发生 | 跑一次 finalize 会重新归档；再犯→查 `archive_expired()` 是否被绕过，转开发 AI |
| PENDING_URLS 待处理区堆积 | 上次 finalize 失败 | 手动跑 finalize；再查该次运行日志 |
| 仓库数据被改乱 | 有人手改了生成产物 | `git fetch && git reset --hard origin/main` 回到远程状态，重跑 finalize |

**回滚方法**（改动已推送但发现问题）：

```bash
git fetch origin
git revert <出问题的 commit sha>    # 生成一个撤销提交，安全
git push origin main
```

**绝对不要** `git push --force`（会丢掉 Actions 的数据提交；workflow 自己内部的
force-with-lease 除外）。

## 六、用户最常用的操作：提交新羊毛网址

任何 AI/人都可以教用户这样提交：

1. 打开 `PENDING_URLS.md`，在「待处理」区写一行（每行一条）：

   ```markdown
   https://example.com/some-deal # ai
   ```

   - `#` 后是分类注释（可选）：`ai` / `games` / `drive` / `open-source` / `shopping` /
     `video-vip` / `netdisk-vip` / `game-discount`；不写则按 URL 自动判断
   - 也可以写自然语言（如 `Qoder现在每天领100积分 #ai`）——由 AI 理解，但它**不能联网核实**，
     描述要自带可验证信息；最可靠的还是直接给官方活动页 URL

2. 等每天 18:47 的 finalize（或手动触发）：URL 会被登记进 `data/sources.json`、
   **当场抓一次内容**，抓到的活动直接入库，处理结果自动记录到「已处理」区
3. 注意：单次提交=抓一次快照。想让某网站**每天被查**，要在 `blog_collector.SOURCES`
   等处加为日常轮询源（见 [自定义](自定义.md)，属于开发活，找开发 AI）

## 七、红线（做了会搞坏仓库，日常 AI 必须记住）

1. **不要手改** `data/*/activities.json`、`docs/calendar.svg`、`docs/data/*`、
   `README.md`、`docs/分类活动.md`、`docs/archive/*`——全是脚本生成的
2. **不要 force push** 到 main
3. **不要改 `scripts/` 里的代码**（那是开发 AI 的活）；唯一允许改的是
   workflow env 里的 AI 配置三行（第三节）
4. **不要把任何 key/token 写进代码或文档**——只放 GitHub Secrets
5. **commit message 用中文**，前缀 `feat:` / `fix:` / `chore:` / `docs:`
6. 不确定的事，**问用户**，别猜
